# Second-look review: upstream catch-up (pull request #1)

**Verdict: merge after fixes.** The fixes are in this pull request (branch `cloud/upstream-review`). Merge this one into `cloud/upstream-catchup` first, then merge #1. One item (Google Drive, finding 3) needs your decision. It does not block the merge, but read it first.

## The short version

- The merge itself is careful. All 7 conflict fixes listed in `MERGE_NOTES.md` match the code, and nothing from the fork was lost.
- **But upstream added a new gate that the merge notes missed.** Before the AI runs, upstream now writes down which tools this one request may use. Any tool not on that list is refused. Your `ckb_preflight` tool was never on it, so it could never run. That meant every CKB-changing GBrain action was also refused, because those need a preflight first. Your code was all still there, but it could not be reached. The existing tests missed this because they build that tool list by hand.
- I fixed that (finding 1) and one small bookkeeping gap (finding 2). Both fixes have tests that fail without them.
- The same new gate also blocks the Google Drive MCP and every other add-on MCP server. That is upstream's deliberate security choice, so I did not override it. You decide (finding 3).
- Tests: the same 80 failures and 58 errors as upstream on its own, with the exact same test names. The merge adds no new failures. My fixes add 6 tests, and they all pass.

## Findings

### 1. Fixed: `ckb_preflight` and GBrain tools were refused by upstream's new per-request tool list

- **Where:** `src/agent_runtime/authority.py:495` (new line), `src/ckb_guardrails.py:216` (`fork_request_tools`) and `:258` (`fork_contract_tools`), `routes/chat_routes.py:141` and `:3786`.
- **What was wrong:** upstream's `create_request_authority` builds an allow list of tools for each message. It only lets in an add-on MCP tool when two things are true: an admin listed it in an environment setting, and you typed its full internal name, like `mcp__gbrain01__search`. `ckb_preflight` was never let in at all. So a call to it came back with "The exact operation is outside server request authority." This gate runs before your CKB guard, so your guard never got a turn.
- **A second, smaller wall:** for models on the "compact" tool setting (the default unless you set a model to "full"), upstream also trims the tool menu for each message. That trimmed menu never included `ckb_preflight` or GBrain tools. Asking "search gbrain for X" got web search instead.
- **The fix:**
  - The allow list now includes `ckb_preflight` for admins, GBrain read tools for everyone, and GBrain write tools for admins.
  - The trimmed menu adds these tools only when the message mentions CKB, GBrain, or your knowledge base, or when a GBrain approval is waiting. That way "Approve once" still works, and upstream's narrow menus stay narrow for everything else.
  - Your CKB guard still makes the final decision on every GBrain call: admin only, preflight done, one exact approval.
- **One deliberate change:** non-admins no longer get `ckb_preflight`. It returns the text of your CKB files, and non-admins can't make the GBrain changes that need it anyway.
- **How to check:** `python3 -m pytest tests/test_ckb_guardrails.py -q`. The new tests `test_request_authority_admits_fork_tools_for_admin`, `test_ckb_preflight_runs_under_real_request_authority`, `test_approved_gbrain_call_runs_exactly_once_through_dispatcher` and `test_turn_contract_offers_fork_tools` use upstream's real gate, not a hand-built list. To see the old failure, undo the line in `authority.py` and run them again. Four of them fail.

### 2. Fixed: `ckb_preflight` was missing from upstream's action log

- **Where:** `src/tool_execution.py:2512`.
- **What was wrong:** upstream now logs every tool run in an "action journal". Every tool branch wraps its call in `dispatched(...)`. The re-added `ckb_preflight` branch didn't, so its log entry stopped at "allowed" and never said "ran".
- **How to check:** `python3 -m pytest tests/test_ckb_guardrails.py -q -k dispatched`.

### 3. Needs your decision: the Google Drive MCP (and every other add-on MCP server) is now blocked

- **Where:** `src/agent_runtime/authority.py:375` (`_trusted_local_mcp_request_tools`).
- **What happens:** before the merge, admins could use any connected MCP server. After the merge, upstream only allows an add-on MCP tool when an admin has listed it in `ODYSSEUS_LOCAL_MCP_READ_TOOLS` or `ODYSSEUS_LOCAL_MCP_WRITE_TOOLS`, and the server runs locally as a "stdio" process, and you type the tool's full internal name. Your Google Drive MCP runs as a web service on port 3001 (`docker-compose.vps.yml`), so no setting can unlock it. The AI will no longer be able to use Google Drive.
- **Why I didn't change it:** this is upstream's main new protection against prompt injection from outside content. Opening it up for every MCP server is a security call for you to make, not something to slip into a merge. GBrain got an exception (finding 1) because your CKB guard already protects it.
- **Your options:** (a) accept the loss for now and merge; (b) ask for a follow-up that gives the Google Drive tools the same kind of exception, ideally read-only tools only.
- **How to check:** after the merge, ask the agent to search your Google Drive. The tool call comes back "outside server request authority".

### 4. Already true before the merge: non-admins never see GBrain tools

- **Where:** `src/agent_loop.py:21550` (`mcp_mgr = None` for any user with blocked tools), and in upstream's new code, `routes/chat_routes.py:3685`.
- **What happens:** the fork's "Phase 6" plan says non-admins can use GBrain read tools, and the dispatcher and guard do allow that. But the agent loop hides every MCP tool from non-admins before the AI sees the list. So non-admins can't use GBrain in practice. `main` behaves the same way, so the merge didn't cause this.
- **How to check:** `git show origin/main:src/agent_loop.py | grep -n "mcp_mgr = None"` shows the same line on `main`.

### 5. Extra approval clicks after GBrain reads (upstream's design, working as built)

- **Where:** `src/tool_capabilities.py:97` (how `ckb_preflight` is classed) and upstream's "after outside content" gate.
- **What happens:** upstream treats GBrain results and `ckb_preflight` results as "untrusted outside content". After one of them, upstream asks for its own approval before the next GBrain call or preflight in the same run. For a GBrain write, you may see upstream's approval card and then your CKB card, so two clicks.
- **If it gets annoying:** `ckb_preflight` could be classed as trusted, since it only reads files you wrote yourself. I left the stricter setting the merge chose.
- **How to check:** in one chat, run a GBrain search and then a second search. Upstream shows an approval card for the second one.

### 6. Misleading comment: `manage_settings` is still admin-only

- **Where:** `src/tool_security.py:45` (comment) and `src/tool_execution.py:1279` (`_ADMIN_TOOLS`).
- **What happens:** the fork's comment says non-admins may use `manage_settings`. A second list, `_ADMIN_TOOLS`, still blocks it for them, and that's the right call: it changes settings for the whole app, not one user. `main` was the same. Nothing is broken; the comment and the test at `tests/test_review_regressions.py:1415` just overstate it. `manage_memory`, `manage_documents` and `manage_tasks` really do stay limited to the user's own data.
- **How to check:** `grep -n '"manage_settings"' src/tool_execution.py`.

### 7. Small, already in `main`: the guard skips the admin check if the login system errors

- **Where:** `src/ckb_guardrails.py:378` (`except Exception: pass`).
- **What happens:** if looking up a user's role ever throws an error, the guard skips the admin check and goes on to the preflight and approval checks. That fails open. In practice those later checks still stop a non-admin, because non-admins can no longer run `ckb_preflight` (finding 1). This review doesn't change it. A one-line follow-up could make it refuse instead.
